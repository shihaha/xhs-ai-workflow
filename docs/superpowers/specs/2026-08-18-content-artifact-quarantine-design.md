# Task 8 内容产物隔离与延迟回收设计

日期：2026-08-18  
状态：待用户审阅  
适用范围：Task 8 产品与内容工作流

## 1. 背景与问题

Task 8 当前会在素材写入失败、内容包构建失败、系统启动恢复等路径中检查数据库引用，然后直接删除磁盘文件。数据库检查与文件删除不能组成同一个原子事务：检查结束后，其他任务仍可能创建新引用；软链接、目录联接或路径等价关系也可能让文件归属无法被可靠证明。

因此，即使普通测试全部通过，多个任务并发、进程中断或 Windows 路径发生变化时，仍可能误删已经被其他记录使用的正式素材或内容包。

本设计不增加业务功能，只替换 Task 8 的物理文件清理机制。

## 2. 设计目标

- API 请求、任务失败处理和系统启动恢复不得直接永久删除业务产物。
- 任何待清理文件先进入有数据库记录的隔离流程。
- 只有能够证明文件位于可信运行目录、归属明确且没有有效引用时，才允许隔离或删除。
- 不确定、冲突、链接或身份变化一律保留文件并转为人工处理。
- 进程崩溃后能够依据数据库状态继续，不依赖内存线程状态。
- 所有页面状态、日志和清理结果来自真实数据库记录。

## 3. 不在本次范围

- 不修改内容生成、审核、图片页序或内容包格式。
- 不实现小红书自动发布。
- 不修改 Task 1—7 的采集、安卓或模型业务逻辑。
- 不开始 Task 9 前端完整流程和 Task 10 发布验收。
- 不提供用户任意路径的通用文件删除功能。

## 4. 采用方案

采用“登记待回收 → 隔离 → 宽限期 → 再核验 → 删除”的两阶段回收机制。

业务请求只改变数据库状态并登记回收候选，不直接删除文件。独立回收服务通过数据库租约领取候选，重新验证归属后，将文件原子移动到同一运行目录下的隔离区。隔离满 24 小时后，回收服务再次验证数据库引用和隔离文件身份；确认安全才永久删除。

如果任一步无法证明安全，文件保留，记录进入 `needs_human`。

## 5. 数据模型

新增 `artifact_gc_queue` 表：

- `id`：规范 UUID。
- `owner_type`：`material` 或 `content_package`。
- `owner_id`：原业务记录 ID。
- `relative_path`：原始受管相对路径。
- `expected_sha256`、`expected_size_bytes`：登记时已知的文件身份。
- `state`：`pending`、`claimed`、`quarantined`、`deleted`、`needs_human`、`cancelled`。
- `reason`：产生回收请求的业务原因。
- `not_before`：允许第一次隔离或最终删除的时间。
- `lease_token`、`lease_expires_at`：单一回收者租约。
- `quarantine_path`：隔离后的受管相对路径。
- `attempt_count`、`last_error_category`：真实重试与失败事实。
- `created_at`、`updated_at`、`completed_at`。

约束：

- 同一 owner 和同一规范路径最多存在一个未结束回收记录。
- 状态、大小、哈希格式和时间字段具有数据库 CHECK。
- `relative_path` 与 `quarantine_path` 都必须是运行目录内的受管相对路径。
- 不对已删除的业务 owner 做级联物理删除；回收事实必须保留。

## 6. 内容包构建者身份

`content_packages` 新增 `build_token`。预约构建时生成随机 token，成功与失败收尾都必须通过一次条件更新同时匹配：

- package ID
- content item ID
- revision ID
- `status = building`
- package path
- build token

成功收尾与内容项转为 `exported` 必须在同一 SQLite 事务内完成。条件更新失败表示构建资格已经丢失：当前构建者不得修改其他记录，只能登记自己生成文件的回收候选。

失败收尾也使用完全相同的身份条件，不允许仅凭 package ID、状态和路径把其他构建者的预约改为失败。

## 7. 文件生命周期

### 7.1 登记

素材或内容包失败后：

1. 业务记录先以事务方式写入真实失败状态。
2. 同一事务中写入或幂等获取 `artifact_gc_queue` 记录。
3. 返回业务错误或失败结果。
4. 不执行物理删除。

若事务结果不确定，系统不得猜测文件无人使用；只记录日志并保留文件，等待恢复扫描。

### 7.2 隔离

回收服务通过 `pending → claimed` 条件更新取得唯一租约，然后检查：

- 路径解析后位于配置的运行目录。
- 不是软链接、目录联接或其他无法证明身份的重解析路径。
- 文件是普通文件，大小和哈希符合登记值。
- owner、路径和文件身份与数据库记录一致。
- 没有任何有效 material、ready/building package 或其他回收者引用同一 Windows 等价路径或物理文件。

检查通过后，文件只能在同一运行卷内原子改名到：

`artifacts-quarantine/{gc_id}/{original_name}`

移动成功后写入 `quarantined` 和新的身份信息。移动或提交结果不确定时保留现状，并进入 `needs_human`，不得尝试猜测性删除。

### 7.3 最终删除

默认宽限期为 24 小时。到期后重新领取租约并进行第二次完整检查：

- 原业务路径没有重新产生有效引用。
- 隔离记录仍属于相同 GC 任务。
- 隔离文件路径、大小、哈希和物理身份没有变化。
- 没有其他数据库记录引用该隔离文件。

全部通过才永久删除，并将状态写为 `deleted`。哈希、大文件读取、移动和等待不得占用 SQLite 写事务；唯一例外是最终删除时，在已打开并绑定物理身份的删除句柄上，以极短 `BEGIN IMMEDIATE` 事务重新核对租约与全部引用、执行句柄删除并写入 `deleted`，从而阻断授权后插入新引用的竞态。无法证明则为 `needs_human`。

## 8. 启动恢复

应用启动时不得删除文件，只执行数据库恢复：

- 遗留 `building` 内容包转为 `failed`，并登记回收候选。
- 过期 `claimed` 租约退回 `pending`，增加真实重试次数。
- `quarantined` 记录保持等待宽限期。
- 数据库与磁盘不一致时登记 `needs_human`，不自动猜测归属。

回收服务启停不得阻塞 Web 应用关闭；所有可恢复状态必须已经持久化。

## 9. 接口和页面状态

V1 不提供任意文件删除 API。新增只读管理接口：

- `GET /api/v1/artifact-cleanups`
- `GET /api/v1/artifact-cleanups/{id}`

返回真实状态、原因、重试、时间和人工处理说明。Task 9 只需显示摘要和 `needs_human` 提示，不提供绕过校验的“强制删除”按钮。

现有 material/package 可用性仍依据真实文件和数据库状态计算。进入隔离的原产物不得继续显示为可用或 ready。

## 10. 错误处理

- 路径不可信、链接/联接、身份不一致：`needs_human`，保留文件。
- 文件已不存在：在确认没有引用后记录 `deleted`，并注明 `already_missing`。
- 数据库锁或临时 I/O 错误：租约到期后有界重试。
- 哈希或大小变化：`needs_human`，不得删除。
- 租约丢失：当前工作者立即停止，不修改文件或其他记录。
- 日志不得包含 API Key、Cookie 或文件正文。

## 11. 迁移

- 新建 GC 表和内容包 `build_token` 列，使用显式迁移标记及物理 schema 校验。
- 现有 `ready` 和 `failed` 包不自动删除。
- 启动时遇到旧 `building` 包，只转失败并登记候选。
- 无法证明来源的历史文件保留并标记 `needs_human`。
- 迁移失败时数据库健康状态必须为不可用，不能等到首个业务请求才暴露。

## 12. 验收测试

- 单元测试：状态机、租约、幂等登记、build token 条件更新、路径规范和宽限期。
- 并发测试：两个回收者、引用在检查期间变化、构建者资格被替换、应用重启。
- 文件测试：大小写/NFC 等价路径、软链接、目录联接、文件身份变化、跨目录替换。
- 故障注入：移动成功但提交失败、提交成功但响应中断、删除前数据库锁、进程崩溃。
- 恢复测试：过期租约恢复、旧 building 包、已隔离文件、文件缺失。
- 集成测试：页面/API 状态与数据库和磁盘一致。
- 完整后端回归及独立代码复审必须无 Critical/Important。

## 13. 完成条件

- 业务请求、失败收尾和启动恢复中不存在直接永久删除。
- 任何模糊归属都保留文件并产生可见的人工处理事实。
- 成功与失败内容包收尾完整绑定唯一构建者。
- 隔离和最终删除均由持久化租约驱动，可崩溃恢复。
- Task 8 独立复审为 CLEAN 后，才解除阻塞并开始 Task 9。
