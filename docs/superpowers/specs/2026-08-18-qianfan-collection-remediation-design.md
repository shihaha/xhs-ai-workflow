# Qianfan Eight-Scope Collection Remediation

Date: 2026-08-18
Status: approved supplement to Task 5

## Purpose

Close the backend acceptance gap left by Task 5 and exposed during Task 9 review: the application has a controlled Qianfan page adapter and a manual snapshot-import API, but no HTTP operation that reserves and runs the fixed four-board by two-dimension collection.

This supplement does not claim that the current Qianfan site selectors or response scope fields have been live-verified. The tutorial proves the eight business scopes, but the attached article does not provide a machine-verifiable current selector contract. Therefore the production selector profile is versioned and explicitly `unsupported` until a real authenticated probe validates it. Unsupported, logged-out, captcha, layout, or unverifiable-scope states become `needs_human`; they never create a Radar snapshot.

## Fixed scope and trust boundary

- Boards are server constants: `阅读榜`, `引流榜`, `热卖榜`, `成交榜`.
- Dimensions are server constants: `优秀内容`, `优秀账号`.
- One POST reserves exactly eight durable scope jobs in deterministic board/dimension order and returns HTTP 202.
- The only request field is `expected_count_per_scope`; clients cannot supply URLs, selectors, JavaScript, executable paths, profile paths, dates, or selector-profile versions.
- Browser executable and persistent browser user-data directory come only from `Settings`.
- The service owns one serial worker. It never runs two scopes concurrently.
- `source_date` and `collected_at` are generated by the backend clock at execution time.

## Adapter and selector profile

`QianfanSelectorProfile` is immutable and versioned. It defines whether live operation is supported plus the fixed page/readiness, authentication, board, dimension, and active-scope verification contract. HTTP cannot select or alter a profile.

The repository default is deliberately unsupported because no authenticated current-layout probe has verified selectors and response scope fields. Tests inject a controlled supported profile and a deterministic page double to prove the complete eight-scope orchestration without presenting it as live verification.

For every scope, the adapter must prove all of the following before returning a complete result:

1. the fixed board and dimension were selected;
2. the UI reports that exact board and dimension as active;
3. the captured ranking response belongs to that exact scope;
4. expected, accepted, rejected, missing, overflow, and duplicate counts satisfy the existing `CollectionResult` contract;
5. raw HTML and response evidence were persisted and attached to that scope job.

If any proof is absent, the result is `needs_human` (or `failed` for a contradictory/overflow result), not `succeeded`.

## Orchestration and persistence

`POST /api/v1/radar/qianfan-collections` creates eight `qianfan_ranking_scope` jobs before scheduling work. Each job input records only server-owned batch ID, fixed scope, expected count, and selector-profile version. Startup converts queued/running jobs of this type to `needs_human/worker_restart_required`; browser navigation is never resumed implicitly after a process restart.

For each reserved job, the serial worker:

1. claims the job;
2. opens the configured persistent Playwright profile;
3. collects and persists one raw evidence artifact;
4. verifies the exact scope and exact N/N result;
5. maps every accepted row into all Radar fields (`rank`, title, author, publication, read, click, pay, GMV, note ID, user ID, source URL, raw evidence);
6. creates/replaces that one Radar snapshot only after the preceding checks pass;
7. finalizes the scope job from the persisted outcome.

Snapshot evidence binds the scope job ID, evidence artifact path, SHA-256, selector-profile version, board, dimension, source URL, and capture counts. A partial, rejected, duplicate, overflow, unsupported, login, captcha, layout, scope-mismatch, mapping, or persistence outcome does not ingest.

An eight-scope batch may therefore truthfully finish with seven snapshots and one `needs_human` job. Neither the API nor job progress may describe that as 8/8.

Every executed collection receives a database autoincrement sequence. Snapshot reads for a source date expose only the latest sequence, so a later same-day 7/8 retry cannot borrow an older scope and appear as a mixed-generation 8/8. Timestamps and UUID lexical order are not used as the ordering authority.

## Lifecycle and configuration

The project declares the Python Playwright dependency. `Settings` adds the persistent Qianfan profile directory. A missing/nonexistent browser executable or profile directory is a real configuration failure surfaced through the reserved jobs; it is not silently replaced by a temporary profile.

Application startup constructs the Qianfan collection service after the database/job/Radar services. Lifespan shutdown closes admission and cancels queued work without blocking forever on an external browser call. The service is closed before SQLite.

## Acceptance tests

- Profile tests prove the default live profile is unsupported and that HTTP cannot inject selectors, URLs, JavaScript, profile paths, or versions.
- Adapter tests prove exact active-scope/response-scope verification and `needs_human` behavior for unsupported, login, captcha, layout, and mismatch states.
- Service tests prove one POST reserves exactly eight jobs, one serial worker executes them, and 7/8 never becomes 8/8.
- Mapping tests prove every Radar field and evidence binding is preserved.
- An empty-database controlled integration produces exactly eight distinct snapshots only when all eight scope results are exact and complete.
- Startup/shutdown tests prove interrupted jobs require human restart and the HTTP boundary returns 202/503 truthfully.
- A live smoke remains `not_run` while `browser_executable` or the persistent profile is unavailable; controlled fixtures are never reported as live Qianfan verification.
