## 2. 已确认的整体业务架构

当前把完整流程明确拆成四段：

### A. 需求雷达系统（当前仓库，已实现主干）

目标：回答 **“什么方向值得继续研究？”**

输出：经过真实证据支持、需要人工决定的 Opportunity。

### B. 产品研究 / 产品定义（当前是独立工作段）

目标：回答 **“这个机会如果要做，具体应该做什么产品？”**

典型动作：

- 深入阅读 Phase A 的需求/商品/笔记证据；
- 必要时购买或取得合法的真实竞品交付样本；
- AI 逐份分析竞品的用户、用途、交付物、结构、价格、体验、同质化和缺口；
- 人与 AI 讨论目标用户、核心问题、产品形态、内容/功能边界；
- 形成一个或多个具体产品候选方案；
- 最终由人决定：立项 / 继续研究 / 放弃。

**当前决定：B 暂不强行做成 `xhs-ai-workflow` 内部自动化模块。**

原因：教程只描述了这段人机协作方法，分享版未把它完整工程化；我们也还没有足够多真实产品案例来证明哪些步骤是真正通用的。

### C. 产品制作（当前是独立工作段）

目标：回答 **“把已经确定的产品方案真正做成可交付成品。”**

根据产品类型分支：

- 虚拟资料：AI 辅助规划结构、分模块制作、人工逐段验收、最终文件验收；
- 网站 / 小程序 / 本地软件：单独 Codex 开发项目，先原型/视觉确认，再 UI，再业务逻辑，再真实用户路径 UAT；
- 其他产品：按其产品形态选择合适的独立制作流程。

**当前决定：C 也暂不做成需求雷达系统内部的自动制造功能。**

Codex 可以参与 C，但应作为“独立产品开发工作段”执行，而不是让当前需求雷达后台在没有人工立项的情况下自动创建产品。

### D. 内容系统（产品完成后再接入）

目标：回答 **“围绕已经完成、已经验收的产品，如何持续研究和生产小红书获客内容？”**

入口前提：必须已经存在真实、可交付、经人工验收的产品及其完整资料。

后续典型链路：

`完整产品资料 → 产品分析 → 关键词布局 → 对标采集 → 单篇拆解 → 模板聚类 → Skill → 日更生成 → 内容审查 → 人工审核/发布`

不要把内容系统当作产品制作系统。

## 3. 两个明确的“断点”

当前完整链路中保留两个有意的人机协作断点：

### Gap 1 — Opportunity → Product Definition

输入：需求雷达输出的 approved Opportunity。

输出：人工批准的具体产品定义。

在没有产品定义之前：

- 不创建正式产品；
- 不开始 Codex 开发；
- 不进入内容系统；
- 不根据 Opportunity 标题自动猜产品形态。

### Gap 2 — Product Definition → Finished Product

输入：人工批准的具体产品定义。

输出：真实可交付、经过人工 UAT 的 Finished Product。

在 Finished Product 完成之前：

- 不进入内容日更；
- 不把草稿/原型/测试文件冒充正式产品资料；
- 不生成“可发布内容包”来假装已经具备销售条件。

## 4. 当前阶段的最小接口思想

虽然 B/C 暂时独立执行，但 A → B → C → D 之间必须有清晰信息交接，避免每次靠聊天口述。

### A → B：Opportunity Research Brief

需求雷达至少能提供：

- Opportunity ID / title / summary；
- supporting accounts；
- common demand；
- commonalities / differences / rationale；
- 商品价格、可见销量、商品形态；
- 笔记证据；
- evidence IDs / artifact IDs；
- 已知限制与未知项；
- 当前人工决定及时间。

B 阶段不得丢失这些事实，也不得把模型推断冒充原始证据。

### B → C：Approved Product Definition

产品研究完成后，应明确输出：

- 目标用户；
- 核心问题 / 购买动机；
- 使用场景；
- 产品形态；
- 核心模块 / 功能；
- 交付物；
- 差异化理由及其证据；
- 不做什么；
- 风险 / 版权 / 平台边界；
- 人工立项决定。

C 阶段只根据被人工批准的定义制作，不自行扩大范围。

### C → D：Finished Product Dossier

内容系统入口需要的是已完成产品的事实资料，而不是 Opportunity。

至少包括：

- 产品名称 / 版本；
- 目标用户；
- 核心需求与场景；
- 核心功能/内容；
- 实际交付物清单；
- 使用方式；
- 价格/购买方式（若已确定）；
- 页面截图/成品截图；
- 使用说明；
- FAQ；
- 能说与不能说的产品 claims；
- 原始产品资料索引；
- 成品版本 / 文件 manifest / hash（适用时）；
- 人工 UAT 状态。

D 不得根据缺失信息自行编造产品事实。

## 5. Codex 当前任务边界

当前 Codex 应先理解并保持上述架构，不要擅自把 B/C 自动化写进主系统。

除非用户后续明确授权，当前不要：

1. 自动生成产品；
2. 自动批准 Opportunity；
3. 自动进入内容生产；
4. 为“七宗罪”直接决定产品形态；
5. 把 Phase B / C 强耦合进 `xhs-ai-workflow`；
6. 修改历史 analysis/evidence 以配合新目标。

当前最重要的工程原则：

> `xhs-ai-workflow` 先稳定承担 Opportunity discovery；产品研究和产品制作先作为独立工作段真实跑通；真实跑过若干产品后，再判断哪些重复步骤值得系统化。
