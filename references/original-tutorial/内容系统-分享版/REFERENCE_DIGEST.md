## 1. 分享版定位

README 原始定位是：**小红书内容自动化系统**，以 Obsidian 工作区形式提供一个完整虚构案例。

正式使用时，要求 AI Agent 先读取：

- `系统地图.md`
- `agents/主代理调度.md`

这套系统的入口前提是：**已经存在完整产品资料。**

## 2. 总体链路

`系统地图.md` 给出的工作链：

```text
完整产品资料
  ↓
产品资料整理 → 关键词布局 → 手机采短链 → 电脑端自动入库 → 单篇拆解 → 模板草案
                                                        ↓
                                      人与 AI 共同固化为生产模板
                                                        ↓
                            按模板日更 → 内容与视觉审查 → 人工审核 → 自行安排发布
```

这说明它负责的是“产品已经存在之后的内容研究与内容生产”，不是从 Opportunity 研究产品、也不是把产品本身做出来。

## 3. Agent 角色

分享版角色树：

```text
用户选择的 AI 工具
└── 主代理：安排研究和日更任务，更新工作台状态
    ├── 产品分析子代理
    ├── 关键词布局子代理
    ├── 单笔记拆解子代理
    ├── 模板聚类子代理
    ├── 日更生成子代理
    └── 日更内容审查子代理
```

主代理和子代理不绑定 Claude Code、Codex 或其他特定 AI 工具。

`<产品目录名>` 是产品、关键词、对标、模板、日更内容之间的稳定关联标识。

## 5. 产品分析 Agent 的真实职责

`agents/产品分析.md` 的角色是：**为小红书内容策略打底的产品分析师**。

输入是：

```text
01-产品/<产品目录名>/原始资料/
```

输出是：

- `产品总览.md`
- `资料索引.md`
- `整理资料/` 下按产品实际内容整理的资料

它不是“研究市场后决定应该做什么产品”的 Agent。

它默认产品已经存在，只负责把真实产品资料整理成后续内容研究可调用的事实库。它明确规定：

- 原始资料保留，只在整理资料里新建整理结果；
- 只从用户给的信息提炼，绝不编造；
- 信息不足写“待补充”；
- 推断必须标 `[推断]`；
- 不产出关键词、不写小红书文案；
- 如果“是什么 / 给谁 / 解决什么”三块里有两块无法确认，要先追问，不直接交空画像。

产品总览使用 9 节框架：产品本体、基本信息定位、视觉出片属性、目标人群、核心痛点和情感动机、使用场景、核心卖点、购买顾虑、竞品/替代/信任背书。

## 6. 关键词布局 Agent

`agents/关键词布局.md` 从产品总览和资料索引出发，把产品画像翻译成**找小红书对标用的关键词网**。

关键词来源覆盖：

- 主词/品类词
- 定位/价格带词
- 视觉/出片词
- 人群词
- 痛点/情绪词
- 场景/时机词
- 卖点/成分词
- 疑问/决策词
- 对比/替代词

默认总数 10～20 个。

每个词有 `expand`、`scope`、`count` 等采集参数；A-Z 扩展只建议给少量短主词使用。

## 7. 手机采集 + 电脑入库

工具索引 `工具/SKILL.md` 将采集拆成：

- `phone-collector/`：手机按关键词搜索、打开笔记、拿分享短链、可选采评论；
- `fetch-note/`：已有短链后，用 Ego 浏览器取正文、话题、互动数据、图片或视频，并固定入库。

标准链路：

```text
关键词和面板采集设置
  └─ collect-keyword
       → 手机采笔记短链 + 可选完整评论
       → 自动入库队列
       → 单篇资料包：正文、图片或视频、互动数据、来源关键词和评论
```

关键运行规则：

- 手机采链、电脑解析；
- 串行，不高频并发；
- `count` 是每个实际搜索词需要拿到的达标笔记数；
- 达标条件主要看点赞 + 收藏是否超过门槛，评论数不参与筛选；
- 低互动过滤，单篇取数异常跳过并继续；
- 同产品全部关键词共用去重记录；
- 已采正文但后来新增“采评论”，只补评论，不重复下载正文和图片。

视频资料包可保存原视频、预览、封面、关键帧和语音稿，但**视频只供人查看，不进入当前 AI 拆解、聚类、模板、日更链路**。

## 8. 单篇拆解 Agent

分享版强调：**一次只拆一篇。**

目标是把一篇笔记拆成可复用结构，而不是总结“这篇很好”。拆解关注：

- 标题公式；
- 正文结构；
- 封面与内页分工；
- 开头钩子；
- 互动数据与内容结构的关系。

避免一次塞十几篇导致 A 的标题、B 的正文、C 的图片混在一起。

## 9. 模板聚类 Agent

一批单篇拆解完成以后，模板聚类 Agent 主要比较**结构化拆解结果**，而不是重新把所有原文混在一起读。

聚类维度包括内容角度、标题结构、正文骨架等。

分享版规则：同类至少要有 3 篇对标支撑，才生成一份模板草案；只有 1～2 篇就继续采，不把偶然写法固化成长期规则。

## 10. 模板草案 → SKILL.md

`模板说明.md` 只是研究结论；真正进入生产的是同目录 `SKILL.md`。

`SKILL.md` 必须明确：

- 产品资料引用；
- 标题公式；
- 正文处理步骤；
- 话题策略；
- 封面和每张内页的职责；
- 用哪个图片 Skill / 脚本；
- 输出文件格式和顺序；
- 禁止写什么。

其中“产品资料引用”是硬约束：必须引用当前产品目录下真实存在的**具体文件**，不能引用模糊目录、其他产品或虚构资料。

演示模板 `模板A-清单型/SKILL.md` 就是：

```text
选择一个用户问题
→ 按“适合谁—步骤A—步骤B—步骤C—注意事项”组织内容
→ 生成封面和内页
→ 输出标题、正文、话题和全部图片
```

并明确“只使用引用资料中的产品事实”“不编造价格、效果和评价”“不操作发布页面”。

## 11. 主代理调度

`agents/主代理调度.md` 的最高层逻辑是：**先日更，再研究。**

优先级：

1. `00-表盘/日更任务.md` 存在时先恢复当前日更；
2. 有成品模板且当天有日更缺口时，先补齐日更；
3. 没有日更任务/缺口时，才处理一个研究队列待办。

研究队列顺序：

```text
Step 1 产品分析
Step 2 关键词布局
Step 3 采集对标笔记
Step 4 单笔记拆解
Step 5 聚类成模板
```

模板草案生成后停止；“模板工坊”由人和 AI 在外部会话共同把草案固化成成品 Skill。成品模板才进入日更。

## 12. 日更生产与审查

日更严格串行：

```text
生成 → 审查 → 返工 / 通过 → 下一个模板
```

日更生成 Agent 一次只处理一个产品和一份 Skill：

- 先读产品总览和资料索引；
- 再读 Skill 明确引用的产品文件；
- 生成标题、正文、话题、封面、内页图；
- 组成完整内容包。

审查 Agent 是新的独立 Agent，会重新读产品资料和同一份 Skill，再审刚生成的内容包。

审查内容包括：

- 产品事实是否错误或编造；
- 标题/正文/话题是否符合 Skill；
- 内容包完整性；
- 必须逐张打开封面和内页做视觉审查；
- 文字是否乱码/截断/重叠；
- 排版、层级、对齐、留白；
- 圈选、箭头、序号、标注是否指对对象；
- 图片与本篇标题正文是否一致。

无法实际打开任一图片时，只能 `阻塞`，不能判通过。

审查不通过就把明确修改意见退回原生成 Agent，修改后再次审查。

## 13. 人工审核与发布边界

分享版明确：

- 新 Skill 开始跑时可以开启人工审核；
- 连续几篇稳定后才考虑减少人工检查；
- 主流程不打开小红书发布页、不调用发布工具；
- 审核后的内容由用户自己的发布方式承接。

## 14. 为什么它不是产品制作系统

这套分享版的第一个正式输入就是 `01-产品/<产品目录名>/原始资料/`，默认产品已经存在。

它的“产品分析”是**把现有产品讲清楚，以便做内容**；不是：

- 从一个市场 Opportunity 深挖竞品；
- 研究用户到底需要什么；
- 决定 PDF / 网页 / 小程序等产品形态；
- 设计产品功能/目录；
- 制作和验收产品本体。

因此完整业务链必须理解成：

```text
需求雷达
→ 产品研究/定义（独立断点）
→ 产品制作（独立断点）
→ Finished Product
→ 内容系统
```

## 15. 与当前工程的关系

当前 `xhs-ai-workflow` 现阶段主要承担 A — Opportunity discovery。

以后真正接内容系统时，入口不应该直接吃 Opportunity，而应该吃 **Finished Product Dossier**：真实产品名称/版本、目标用户、核心需求、实际功能或内容、交付物、使用方式、截图、FAQ、可说与不可说的 claims、版本与 UAT 状态等。

详细接入边界以 `docs/CODEX_NEXT_OBJECTIVE.md` 为准。
